# Data: i18n Shape & Helpers

### Bilingual `{ en, pl }` data shape
All user-facing strings — UI chrome, lesson titles, bodies, prompts — are stored as objects with exactly two keys: `en` and `pl`. UI chrome lives in the module-level `UI` map; lesson and exercise content lives inline in the `LESSONS` data. Do not introduce other shapes (no `{en, pl, de}`, no separate locale files, no i18n library).

```js
progressLabel: { en: "Progress: ", pl: "Postęp: " }
```

### Access bilingual fields through `t()` only
Read bilingual fields exclusively through the `t(field)` helper, which resolves to the current language from localStorage. Never inline language checks (`getLang() === "pl" ? x.pl : x.en`) at call sites — every consumer goes through `t()`.

### Thin `localStorage` state helpers as the sole chokepoint
All state access goes through five thin helpers: `getLang`, `setLang`, `getProgress`, `markDone`, `t`. Do not read or write `localStorage` from anywhere else in the file. If you need new persisted state, add a helper alongside the existing ones.

**Why this matters**: Centralizing language resolution and storage access keeps the data contract changeable in one place — important because the same shape doubles as the persisted format.
